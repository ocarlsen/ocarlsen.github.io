Upgrading production models without guessing

Owen Carlsen · Oct 2026

Every few weeks, one of the model vendors I depend on ships something new. At first I read the announcement, tried a few prompts, and switched if it felt better. That works until a new model is worse at your task and a user tells you.

The company I run operates on LLM pipelines: email and Slack triage, code review, captions, images, video and invoices. So I built a process for it. A job checks every vendor's model list every hour. When a newer model appears in a slot I use, I get a one-tap prompt to benchmark it against the current model on a frozen set of my own tasks. Nothing switches until a blind comparison supports it. The switch is a pull request I review, and the canaries that already watch every job's behavior keep watching it afterward.

Pin every model

Every job calls an exact model version. None uses a floating "latest" alias. An alias is an upgrade you never approved. If a vendor repoints it, your job changes behavior overnight and nothing in your repo says why. Some vendors make this easy to avoid. Anthropic now ships every model ID as "a pinned snapshot" (Anthropic, "Models overview"). That doesn't stop your own code from defining a "latest" of its own.

Each pin belongs to a slot, a named role such as "the model that drafts captions" or "the model that judges code reviews", and the pins live in one registry in code. Once an hour, a watcher compares each vendor's published model list against that registry and flags two things: a pinned model the vendor no longer lists, and a newer model from the same family as one I've pinned. It also reads the vendors' announcement feeds, and it makes no model calls.

The watcher doesn't run anything itself. It posts a note to Slack with a one-tap button, and the benchmark runs only when I tap it.

Benchmark on your own work

Public leaderboards tell you which model does best on average, on tasks someone else chose. I need to know whether a model is better at my jobs. So each production job has its own benchmark harness, built from a frozen set of inputs: real ones where I have them, synthetic cases where I don't.

A single command takes any one harness and runs its frozen inputs through two models: the one in production now and the candidate. Before it spends anything, it estimates the cost of the run, scaled by the candidate's price, and refuses to start if the estimate is over a fixed cap.

When I tested which model should judge my voice and chat agents' answers for fabrication, against 99 answers I had labeled by hand, the newest flagship agreed with my labels less often than the older one it would have replaced (83.8% against 88.9%), and it passed an answer containing an invented product detail that the older one caught. If that judge had followed a "latest" alias, it would have gotten worse on the day of the release.

Judge blind

Captions, images and video are judgment calls, so I judge them myself, on a voting page the harness builds for each run. It shows each pair of outputs as A and B, randomized per input, with the key held on the server so I can't peek. I vote A, B or tie, and the tally appears only after every input has a vote.

Text tasks like code review use a model as judge, itself pinned so results stay comparable across dates. Each synthetic case has known defects planted in it. The judge sees only the list of planted defects and the review's findings, with no model names, and reports which planted defects the review caught and how many other findings it raised. I call those unplanted flags rather than false positives, because some of them may be real.

The first decision was a tie

The first candidate through the pipeline was a newer OpenAI model for the caption slot, a public-facing job that runs every time the company posts. At OpenAI's published prices it cost half as much as the model it would replace: $2 per million input tokens against $4, and $10 per million output tokens against $20 (OpenAI, "Pricing").

At half the price it only had to match the current model, so I judged it on captions, the job it would do.

Over 13 frozen inputs, the new model won 5, the current one won 4, and 4 were ties. I called that a tie and switched.

Thirteen votes can only catch a large regression. A modest one would not show at that size. A side check on code review pointed the same way: across 12 planted defects the new model caught 9 and the current one caught 10, while the new model raised about a third as many unplanted flags.

I accepted the remaining uncertainty because the downside was bounded. Each post starts from five candidate captions, each drafted by a different model, and a person picks one and edits it. The OpenAI model writes only one of the five, so a weaker model loses picks, not posts. The behavior canaries that watch every job kept watching this one, and rolling back is reverting one pull request. In the two weeks since, it has run cleanly every time.

The pipeline has also rejected a candidate. A later one from another vendor lost 4 to 6, with 3 ties, and I kept the current model.

What changes besides quality

Defaults change. When I moved from Claude Sonnet 5 to Claude Sonnet 5.5, a request with no thinking setting started thinking: on Sonnet 5.5, adaptive thinking is on by default, at high effort (Anthropic, "What's new in Claude Sonnet 5.5"). My calls never set it, so each one began spending about 360 to 670 thinking tokens, billed as output, before writing a short answer. Turning it off took a value that hadn't existed before: on Sonnet 5.5, the old "disabled" setting returns an error, and the lowest setting is a new one, "between_tools". With that set explicitly, output came back to about 150 tokens.

Token counts change. When I benchmarked a triage job moving from Claude Haiku 4.5 to Claude Haiku 5.5, the same 78 inputs counted about 53% more input tokens. Anthropic's docs put the new tokenizer's increase at approximately 30% and add that "the exact increase depends on the content" (Anthropic, "What's new in Claude Haiku 5.5"). In that case the per-token price had dropped tenfold, from $1 to $0.10 per million input tokens (Anthropic, "Pricing"), so the job still got about six times cheaper. Rerun your own inputs and compare the bill.

At a team's scale

I built this alone, and a single judge voting on 13 inputs is what one person can afford. The shape is the staged release I've run for years on larger systems, from QA through UAT to production, with sign-off from the teams that depend on it, and a model bump deserves the same gate. With a team, I'd keep that shape and change the scale:

  • The pin registry stays in code, with an owner for each slot, and every bump is a reviewed pull request that links its eval.
  • Each team owns the frozen eval set for the jobs it runs, and grows it from real failures.
  • Blind human judging rotates across reviewers, with enough samples to detect the size of regression that matters and to measure whether the reviewers agree.
  • A bump reaches one job or a slice of traffic first, behind the same behavior canaries, with a one-step revert.
  • Cost caps are per run and per team, checked before the run starts.

A model upgrade is a deploy. It gets a diff, a test and a reviewer.

I turned this into a small open-source tool, pinbench: github.com/ocarlsen/pinbench. It turns the process above into a command-line tool: pinned models, a hard cost cap, blind votes, and a stated rule for when to switch.

Numbers about my own pipeline (votes, scores, token counts and run costs) come from its benchmark result files, pull requests and decision log, checked October 17, 2026. They are private, so they are not linked. Vendor prices and defaults are as published on the dates checked.

What I built at Claire Daily Health

Owen Carlsen · Nov 2026

From June 2026 I was the founder and sole engineer of Claire Daily Health, a small San Francisco company. The first plan was a regulated telehealth product, and the company is now closed. This page describes the pipelines I built to run it. The website was only the storefront. The company ran behind it, in the jobs below.

What ran

I built it with Claude Code, in Python, on the Anthropic, OpenAI, Gemini and Meta APIs, with jobs scheduled by launchd. The company's day-to-day work ran on LLM pipelines I designed: email and Slack triage, daily briefs, social content and PR review. That came to 105 scheduled jobs and about 12,000 logged model calls from late June to November.

The split between model and code was deliberate. A model did the judgment: reading a message and deciding what it asked for, writing the brief, reviewing a diff, drafting a post. Plain Python did the mechanics around it: the Gmail and Slack reads, the ledger writes, the schedules, the backups and the checks. 25 of the 105 jobs called a model, and the other 80 were plain Python.

About half of the jobs were canaries. Each one tested one thing and posted to Slack only when the test failed, so a quiet channel meant the pipeline was healthy.

About a third of the calls ran on Claude Sonnet, a third on Claude Opus, a fifth on Claude Fable and a tenth on Claude Haiku. PR review picked its model by the size of the diff.

Most scheduled runs never reached a model. A plain Python pre-step looked for new work first and called the model only when it found some. The Slack agent called a model on about 5 percent of its runs, the email action worker on about 1 percent, and the invoice reader on about 7 percent. Six of the model jobs also ran with a bare prompt: about 400 tokens of fixed context instead of the 75,000 a full Claude Code session loads.

Alerts

The canaries and the reports posted 596 alerts of 85 kinds to Slack between late June and November. 71 percent got an automatic follow-up: a worker read the logs behind the alert and posted a recommended fix in the alert's thread, with a one-tap approval to run it.

Agents and evals

I built the company's AI voice and chat agents and an eval harness for them. The harness held 131 probes in nine suites: 82 grounding questions generated from the company's own content, and hand-written suites for fabrication, medical boundaries, privacy wording, over-refusal, persona and conversation mechanics. An LLM judge read each answer against the source text and passed or failed it. Four suites were zero-tolerance gates, 29 probes in all, and one fail would block the agent from going public.

The harness tested two things: the agent, and the judge that graded it.

Testing the agent. An agent can answer a question well twice and badly once, so each zero-tolerance question ran as three separate conversations, and the judge scored each answer once. One bad answer out of three was enough to block the agent.

Testing the judge. The judge is a model too, so it can be wrong. I graded a sample of answers myself, without seeing its verdicts, and compared. The disagreements I traced came from the test, not the judge: a grading rule that was too loose or too strict, or the test API adding double spaces the live widget never shows. I fixed those, and in the last three rounds the judge agreed with me on every answer.

The harness recorded 452 results on the chat agent across 17 runs. The zero-tolerance questions were asked three times, so those 452 results took 1,166 judge calls (the other 2,441 went to development runs, calibration and trials of newer judge models).

Model upgrades

A job checked every vendor for new releases, and an approved candidate ran blind against the current model on the company's own tasks. Three production models moved that way. The caption model moved to a newer release at half the price. The email triage model moved from Claude Haiku 4.5 to 5.5 after a 78-input blind benchmark. The fifteen jobs on the Sonnet tier moved to Sonnet 5.5. One candidate was held back: Opus 5 and 5.5 both argued past a fabrication when I tried them as the eval judge, so the judge stayed on Opus 4.8. I wrote up how it works in Upgrading production models without guessing. I also built pinbench, an open-source CLI that runs the same blind, cost-capped A/B test on your own inputs before a job switches models.

Cost and memory

The Slack agent's prompt had grown to about 190 KB, and most of each reply's cost was writing it to the cache. I split it into a short router and 20 lane files, one per command, that the agent read only when a message hit that lane. Over the two weeks on each side of the change, the cache write per reply fell from about 88,000 tokens to about 66,000, and the cost per reply fell by over a third.

PR review routed each diff by size. Fable reviewed every pipeline diff of 80 lines or more, which was three in four reviews. Smaller diffs and website changes went to Sonnet, and documentation-only diffs went to Haiku. Fable cost 12 to 14 times as much as Sonnet per review.

Memory lived in 12 stores, one per project, 727 files in all, each loaded only by the sessions that worked in that project. A daily check would flag any store that nothing loaded, any file that would blow the boot budget, and any store missing from the backup.

Parallel sessions

I ran many Claude Code sessions in parallel, one per project. The tooling that keeps their memory current across sessions, and lets me answer them all from one session, is open source as session-notes.

The company’s code is private. The parts that generalize I’ve published as open source: session-notes, pinbench and FrontDesk. On a call I’m glad to walk through the rest, and through the GitHub history and vendor consoles that show it running from June to November 2026. To see the sessions at work, the session-notes README has a film of about five minutes of real Claude Code sessions.
